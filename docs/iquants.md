# Q2_K and the i-quants (Underdog Saluki 27B)

runq loads GGUF tensors of type **Q2_K, IQ1_S, IQ1_M, IQ2_XXS, IQ2_XS, IQ2_S, IQ3_XXS, IQ3_S and IQ4_XS** (2026-10-30),
next to Q8_0 and Q3_K .. Q6_K, in any mix and in any role, the token embedding included. The motivation was
[ConwayResearch/Underdog-Saluki-27B-1.0](https://huggingface.co/ConwayResearch/Underdog-Saluki-27B-1.0): Qwen3.8-27B
(`qwen35`, the architecture runq already ran) as ISTA-DASLab's GSQ-RCO mixed-precision file retuned for tool calling,
7.9 GB, made of exactly these types. The code: [src/iquants.h](../src/iquants.h) (formats, layouts, arithmetic, the
generic and AVX-512 kernels), [src/iq_grids.h](../src/iq_grids.h) (the codebooks, generated by
[tools/gen_iq_grids.py](../tools/gen_iq_grids.py) from ggml's `ggml-common.h`).

```sh
scripts/download_models.py saluki-27b      # 7.9 GB, pinned revision, sha256-checked
runq models/Underdog-Saluki-27B-1.0-GGUF/Underdog-Saluki-27B-1.0-IQ2-mix.gguf -r 0     # chat, thinking off
```

## The file

64 layers (48 linear, 16 attention), dim 5120, no MTP block, untied; Qwen's own Qwen3.8 chat template (byte-identical
to `tests/golden/templates/qwen3.8-hf.jinja`: thinking on by default, `reasoning_effort`); the general.sampling.* keys
(temp 1.0, top-p 0.95, top-k 20; the model card recommends temperature 0.6 with thinking, 0 for direct tool calls).
Types per role (tensors): token_embd IQ1_M; output IQ3_S; ffn_down mostly IQ2_XXS (53 of 64); ffn_gate / ffn_up all nine
types over the layers (IQ1_S, IQ1_M, IQ2_* most); attn_qkv / attn_gate / ssm_out / attention q, k, v, output: IQ2_XXS ..
IQ4_XS, Q2_K, a few Q4_K; ssm_alpha / ssm_beta Q8_0 (not F32 as in Unsloth's 27B files). Weights by type: IQ2_XXS 9.2 G,
IQ3_S 2.9 G, Q2_K 2.7 G, IQ2_S 2.7 G, IQ1_S 2.6 G, IQ2_XS 2.2 G, IQ1_M 1.6 G, IQ3_XXS 1.4 G, IQ4_XS 0.2 G, Q4_K 0.1 G.

## Arithmetic

Every one of these formats dequantizes as an exact fp32 product (ggml's `dequantize_row_*`: d has 11 significant bits,
the scale factor at most 5, the value at most 7; IQ1's delta is 1/8), so each type is `w = D * S * v` with D per row and
super-block (`d`, `d/8` or `d/4`), S an integer per sub-block of 16 or 32 values and v a small integer per value (IQ2:
+-{8, 25, 43}; IQ3_XXS +-{4 .. 62}; IQ3_S +-{1 .. 15}; IQ1: 8 grid +- 1; IQ4_XS its non-linear table; Q2_K q 0..3 with
a min). A matmul output is then the K-quants' fold on runq's int8 activations (groups of 32): per group
`I = S_0 T_0 + S_1 T_1` in int32 (T_h = the sum of v * xq over a sub-block of 16; exact), `val = val + (D * xs) * (float) I`
(Q2_K: minus `(dmin * xs) * (float) M` for the mins), every fp32 operation rounded, in group order. That definition is
the generic kernel `iq_dot`; the AVX-512 kernels compute the same integers (vpdpbusd on the codes biased to u8, the bias
removed with the activation sums of 16 that the K-quant kernels already keep) and the same float operations, so the
logits are bit-identical across builds, thread counts, chunk sizes and batch compositions, as for every other format.

## Layouts and kernels

Weights are repacked at load into 16-row blocks over 256-column super-blocks, as the K-quants: the file's fields of the
16 rows transposed so that each is one vector load (dword lane r = row r), signs as one 64-bit mask per step of 4
columns. The expensive part is the codebooks (IQ2_XXS 256 entries of 8 values, IQ2_XS 512, IQ2_S 1024, IQ3_XXS 256 of 4,
IQ3_S 512, IQ1 2048 of 8): gathers from them (`vpgatherdq` / `vpgatherdd`) run at ~2.5 elements / ns per core on Zen 4,
which made the IQ2 / IQ3 / IQ1 kernels 4-7x slower per weight than Q2_K's. The kernels (AVX512-VBMI: Zen 4, Ice Lake and
later) instead look the indices up in the compact codes of each grid entry (2 or 3 bits per value), held in registers:
`vpermi2b` over 128 entries with a blend tree on the higher index bits (64 lookups per instruction; the indices are
stored lane-major, `byte 4 r + l`, so the lookup output already has each row's codes in its lane), then
`vpmultishiftqb` cuts each step's codes out and `vpermb` maps them to the biased values (a masked `vpermb` on a second
table for the negative ones). IQ1's 2048-entry book is too big for registers: its indices are replaced by their codes at
load (2.2 / 2.4 bits per weight instead of 1.56 / 1.75: +0.34 GB on Saluki), so its decode is shifts and `vpermb` only.
Without VBMI (Skylake-X, Cascade Lake) the AVX-512 kernels gather (IQ1: shifts and `vpshufb`); `RUNQ_IQ_GATHER=1`
selects that decode at run time (a test switch: the suite checks that both give the same logits). NEON and other CPUs
run the generic kernel (correct, slow).

Single-thread GEMV, ns per weight (Zen 4, `/var/tmp`-style microbenchmark of `iq_rows`, 1024 x 5120), gathers -> VBMI:
IQ2_XXS 0.066 -> 0.023, IQ2_XS 0.067 -> 0.028, IQ2_S 0.068 -> 0.034, IQ3_XXS 0.096 -> 0.030, IQ3_S 0.101 -> 0.037,
IQ1_S / IQ1_M (codes) 0.061 / 0.067 -> 0.017 / 0.020; Q2_K 0.014, IQ4_XS 0.013 (no codebook). Saluki's decode went
6.7 -> 10.2 -> 12.7 -> 14-15 tok/s at 16 threads over these steps.

Batched rows (prefill, verify passes, batched decode) take the same kernel with up to 8 activation rows per pass over a
decoded group (`iq_rows`; not the K-quants' tiled GEMM nor their small-batch kernels).

## Measurements

16-vCPU AMD EPYC Genoa VM, 2026-10-30, `scripts/bench_models.py -t 8,16 -r 2` with Unsloth's Qwen3.8-27B Q3_K_M
alongside (best of 2, load 10-17):

| file | weights in RAM | peak RSS (1,500 + 128 tokens, -c 4096) | prefill 488 / 1,532 tok, 8 / 16 threads | decode short / after 1,500, 8 threads | 16 threads | startup, 16 threads | perplexity (512-token windows; full) |
|---|---|---|---|---|---|---|---|
| Saluki 27B IQ2-mix | 7.63 GiB | 8.45 GB | 30 / 54 tok/s | 9.9 / 9.8 | 13.3 / 14.3 | 2.3 s | 11.841; 9.806 |
| Qwen3.8-27B Q3_K_M | 12.4 GiB | 13.3 GB | 42 / 74 | 9.8 / 10.2 | 12.3 / 12.6 | 9.0 s | 10.069 |
| Qwen3.8-27B Q4_K_M | 15.3 GiB | 15.9 GB | 45 / 73 | 7.9 | 9.1 | | 9.800 |

(Perplexity: `scripts/ppl.py bench/ppl_beagle_ch1.txt -w 512` with .venv-hf5, the 27B rows from README.md's table.) So:
~37% less RAM than the Q3_K_M and the fastest 27B decode here at 16 threads; at 8 threads it is compute-bound (the
codebook decode) and as fast as the Q3_K_M; prefill is ~0.72x the Q3_K_M's (the K-quants have a tuned GEMM: a follow-up,
TODO.md); perplexity +18% over the Q3_K_M (the model card's own numbers: tool calling kept, competition math 82-85% of
the full model's). A 64-token greedy decode at 16 threads measured 14.2-15.1 tok/s.

## Validation

- Dequantization: every type, from the file's blocks (embedding rows) and from the repacked layouts (what the kernels
  read), bitwise equal to gguf-py (`gguf.quants.dequantize`) on the Saluki file, rows across 16-row block edges and the
  last rows of each matrix; tests/ggufmini.py's numpy dequantization (the reference forward pass's) bitwise equal to
  gguf-py on real and random blocks of every type (`tests/golden/dequant/iq_blocks.npz`, `make_dequant_golden.py --iq`).
- Logits on Saluki: AVX-512 (VBMI and gather decodes) == generic, bitwise; vs `tests/ref_qwen35.py` on the file's
  dequantized weights (fp32 activations): cos mean 0.99994-0.99998, min 0.99989, top-1 62/62
  (`tests/golden/models/saluki-27b`, the models group's `saluki-27b` entry, opt-in, ~12 min); greedy golden; the 50
  chat renderings (tools, `-e low`) equal HF's; runq serve's greedy, thinking and a constrained reply.
- `make test` (default suite, numpy only): `synth-q35-iq.gguf`, the 27B-shaped synthetic model with its matrices
  requantized to all nine types (tests/iqquant.py, mixed per role as in Saluki's file; IQ1_M embedding, IQ3_S
  classifier): logits vs the numpy reference (cos mean 0.9966-0.9982, top-1 280/338: the int8 activations), batched /
  threads / AVX-512 vs generic / gather vs VBMI bitwise, api_test (32 checks) and its digests across builds, runq's
  dequantization of every type vs ggufmini. 1,323 checks pass (2026-10-30).
